# PLAN.md — Last Mile

## 1. Problem (one paragraph for the pitch)
Pune Metro ridership is below projections, and the stated reason is last-mile connectivity: stations are
3–6 km from where people actually work. Kharadi's IT parks (EON, WTC, International Tech Park) are the
clearest case — the nearest working station is Ramwadi on Line 2, and the only public link is a PMPML
feeder bus every ~30 minutes. Companies keep paying for door-to-door cabs because nobody can show them,
employee by employee, who could switch and what a company shuttle from Ramwadi would need to look like.

## 2. User and job
**User:** transport/admin manager at a mid-size IT company in Kharadi (synthetic: "a 1,200-person company at EON IT Park").
**Job:** decide whether to run a company shuttle from Ramwadi Metro, how often, and justify it to finance.
**Not the user:** individual commuters (no personal trip planner in scope).

## 5. Commute model (`src/model/`) — pure functions
For each employee:
1. `roadKm` = haversine(home, office) × `roadCircuityFactor`.
2. **Cab trip** minutes = `roadKm / peakRoadSpeedKmh × 60`. Cab cost/day = `roadKm × cabRatePerKm × 2`.
3. **Metro trip**:
   - access leg: nearest station (by haversine × circuity) among *open* stations. If access ≤ `walkMaxKm` → walk at
     `walkSpeedKmh`; else auto at `autoSpeedKmh` + `autoWaitMin`, cost `autoFarePerKm`.
     If access > `accessMaxKm` → employee is **not eligible** (reason: "too far from any station").
   - ride: stations between boarding and Ramwadi along the line graph × `minPerStation`;
     each line change adds `transferMin`. Line 3 stations only exist when the "Line 3 open" toggle is on.
   - last mile from Ramwadi: wait = shuttle headway / 2; ride = `ramwadiToOfficeKm / shuttleSpeedKmh × 60`.
     Headway = slider value (company shuttle) or `pmpmlHeadwayMin` (PMPML-only mode).
   - fare: Metro fare by stations travelled from `fareSlabs`.
4. **Verdict**: `canSwitch` if metroMin ≤ cabMin + tolerance (slider, default +10 min) AND eligible.
   Also return `deltaMin` (positive = metro slower) and a short `reason` string.
   Metro trip also adds `metroEntryExitMin` once.
5. **Fleet sizing** (company shuttle only): roundTripMin = 2 × shuttle ride + 10.
   busesForHeadway = ceil(roundTripMin / headway).
   peakRiders = switchers in the busiest `shiftStart`; seatsPerBusPerShift = busSeats × max(1, floor(`shiftWindowMin` / roundTripMin)).
   busesForDemand = ceil(peakRiders / seatsPerBusPerShift). buses = max(busesForHeadway, busesForDemand).
   Monthly shuttle cost = buses × `busMonthlyCost`. In PMPML-only mode buses = 0.
6. **Totals**: switchers, % of workforce, monthly cab spend avoided (switchers × cab cost/day × `workDaysPerMonth`),
   minus shuttle cost, minus metro + auto fares if `companyReimbursesFares` → **net monthly saving**;
   CO₂/year avoided = switchers × roadKm × 2 × `cabCo2KgPerKm` × `workDaysPerMonth` × 12 / 1000;
   breakdown of switchers by boarding station (top 5).

Unit tests (`tests/model.test.mjs`) must cover: haversine sanity (Ramwadi→EON ≈ 3.5–4.5 km straight-line),
an employee next to Vanaz (long cab ride) switches at default settings, an employee next to Kalyani Nagar
does NOT (cab ride already short — this is a real insight, keep it), an employee in Wagholi does not
(no station within reach), Line 3 toggle changes the verdict for at least one Wakad/Hinjewadi employee,
fleet sizing returns ≥1 bus when switchers > 0, PMPML-only mode yields fewer switchers than 15-min company shuttle.

## 6. Visual layer (`src/ui/`)
- `map.js` — project lat/lng to an SVG viewBox using a simple equirectangular projection fitted to the data bounds,
  then **snap stations to a schematic**: lines drawn as straight segments at 0/45/90° between stations
  (transit-diagram style). Employees are small dots placed at projected positions (not snapped).
  Ramwadi → office shuttle loop drawn as a thick amber path with an arrow; animate it once on load
  (stroke-dashoffset), respect `prefers-reduced-motion`.
- Station labels in English; on hover/focus show the Marathi name (Mukta font) too.
- Dot colours: can switch / borderline (within +5 min of tolerance) / cannot. Legend uses words, not colour alone.
- `controls.js`, `results.js`, `memo.js` — recompute on every control change (< 50 ms for 1,200 employees).
- Numbers use tabular figures and Indian grouping (₹18,60,000 → show as ₹18.6 lakh).

## 7. Transport memo (`src/ui/memo.js`)
Deterministic template, no AI call: 120–180 words addressed to "Finance", stating recommendation
(run / don't run shuttle, headway, bus count), switchers, net monthly saving, CO₂, the top 3 boarding stations,
the 3 assumptions with lowest confidence, and the Line 3 note when the toggle is on. "Copy memo" button.

## 10. M7 — Enhancements (added 12:10; known-good fallback commit `a13262b`; hard freeze 4:00 PM)
Build in this order. Each is its own commit and must not change any existing number on screen.

### M7a — "How robust is this recommendation?" (sensitivity test)
- Model: `sensitivity(employees, context, assumptionDocument, { deltaPct: 25 })` in `src/model/`. For every assumption with
  `confidence: "low"` and a single numeric `value` (skip `fareSlabs` and booleans), run `recommendHeadway` with the value
  ×0.75 and ×1.25. Return per assumption: label, low/high value, recommended option at each, net saving at each,
  `changesRecommendation` (bool). Plus a summary: tests run, tests where the baseline recommendation holds.
- UI: new section under the memo, "How robust is this?", with a **Run robustness test** button (computed on click, not on
  every slider move — ~100 model runs). Headline sentence: "20 min stays the best plan in X of Y tests (±25% on each
  low-confidence input)." Then a compact table: input · −25% → plan · +25% → plan, with rows that flip the plan marked in
  `--stay` and words ("changes the plan"), not colour alone. Re-running after a control change uses the new context.
- Tests: baseline recommendation unchanged; every low-confidence numeric assumption appears; a ×1.0 run reproduces baseline.

### M7b — "Why this verdict?" (click a dot)
- Clicking/tapping the map finds the nearest employee dot within 12px (SVG coordinates) and opens a small panel beside the
  map: cluster, cab minutes and ₹/day; Metro path — access mode + minutes, boarding station, ride minutes, transfers,
  shuttle wait + ride; total minutes; verdict + reason. The selected dot gets a slate ring. Esc or clicking empty map closes it.
- All values come from the existing `evaluateEmployee` result — no new maths in the UI.

### M7c — "Use your own workforce" (CSV import)
- A file input reads CSV with headers `lat,lng` and optional `shiftStart` (09:00|10:00|11:00, default 09:00) via
  FileReader — nothing leaves the browser; say so next to the control. Rows outside Pune bounds (lat 18.35–18.75,
  lng 73.60–74.10) are skipped and counted. Banner: "Using your uploaded data: N employees (M rows skipped). Reset to
  synthetic data." Everything (map, rail, chart, memo, robustness) recomputes. Reset restores the synthetic set.
- Ship `data/sample-upload.csv` (≈150 rows, generated by a script, seed 77, labelled synthetic) for the demo.
- Tests: CSV parser handles header order, blank lines, bad rows; out-of-bounds rows skipped.
